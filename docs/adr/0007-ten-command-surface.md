# ADR-0007: Keep a fixed ten-command surface with no daemon

- **Deciders:** mcfuzzysquirrel (maintainer)
- **Date:** 2026-10-31

**Technical Story:** `PRE-FR-06`

## Agent Rules

- **MUST:** register exactly these ten commands: `add`, `list`, `status`, `logs`, `update`, `rollback`, `remove`, `config`, `doctor`, `version`.
- **MUST NOT:** register `start`, `stop`, `restart`, `prune`, `completion`, or a daemon command.
- **MUST NOT:** add a background service, scheduler, webhook receiver, or HTTP API to easy-host.
- **MUST:** add new capability to an existing command or document it as out of scope; do not grow the command list.
- **SHOULD:** generate shell completions from the command definitions into `completions/` rather than shipping a completion subcommand.

## Verify

- **Check:** `npm test -- tests/unit/program.test.ts tests/unit/completions.test.ts tests/docs/links.test.ts`
- **Expected:** the program lists exactly the ten names; the forbidden names are absent; completions mention every command and flag; the documentation tests reject a forbidden command in the README or an operations guide.

## Context and Problem Statement

A CLI with many lifecycle verbs turns into an implicit process manager: `start`, `stop`, `restart`, `enable`, `prune`, `completion`, and eventually a daemon. Each verb adds state transitions and failure modes. How small can the command surface stay while still covering the operator workflow?

## Decision Drivers

- A predictable contract that scripts and systemd timers can branch on.
- No process of our own to supervise, upgrade, or secure.
- Podman already owns container start, stop, and restart semantics.
- Documentation and completions stay small enough to check mechanically.

## Considered Options

- A daemon with an HTTP API and a thin client.
- A rich CLI with per-container lifecycle verbs.
- Ten commands covering app lifecycle, inspection, configuration, and host checks.

## Decision Outcome

Chosen option: "Ten commands covering app lifecycle, inspection, configuration, and host checks", because the operator's unit of work is an app, not a container. `update` and `rollback` own replacement, `remove` owns deletion, and Podman owns start/stop. A daemon would add the very moving part the product exists to avoid.

### Positive Consequences

- The command list, exit codes, and completions are small enough to document exhaustively.
- No easy-host process runs between invocations, so there is nothing to keep alive or patch.
- A systemd timer can call `update` with no IPC.

### Negative Consequences

- There is no command to start a container that an operator stopped by hand; Podman remains the escape hatch.
- Recurring work needs an external scheduler (systemd timer), which the project documents but does not ship.
- Adding a genuinely new workflow either extends an existing command or is rejected.

## Pros and Cons of the Options

### Daemon plus client

- Good, because it enables remote control, scheduling, and a web UI.
- Bad, because it adds a long-running privileged service, an API surface, and an upgrade problem for a single-host tool.

### Rich per-container CLI

- Good, because it mirrors Podman's verbs and is familiar.
- Bad, because it duplicates the runtime's state machine and multiplies the failure modes the tool must document.

### Ten app-level commands

- Good, because it matches the operator's mental model and keeps the contract auditable.
- Bad, because some runtime operations are intentionally left to Podman.
