# v0.1.0 Release Gate — RBK-1.6 Human Review Checklist

Operator checklist for the `human-review` task **RBK-1.6**. This gate cannot be
satisfied by unit tests, and an agent must never run `approve-task` or write the
attestation. The operator runs the scenarios, records the evidence, and then
attests.

- Feature contract: `docs/features/06-rollback-and-remove.md` → RBK-1.6
- Success criteria: `docs/PRD.md` §6.2
- Review file (generated by the CLI, never hand-written):
  `docs/reviews/v1-success-scenarios.json`
- Evidence file (written by the operator):
  `docs/reviews/v1-success-scenarios-evidence.md`

The task text says "four success scenarios", but it enumerates five actions and
PRD §6.2 lists five numbered criteria. Record all five and note the wording
discrepancy in the evidence.

---

## 0. Pre-flight

- [ ] Fresh Linux host (VM/LXC/cloud), not a machine with existing easy-host
      containers, images, or state.
- [ ] A second machine on the same LAN for the reachability check.
- [ ] Rootless Podman 5.7.0–5.8.x, lingering enabled for the owning user.
- [ ] System git >= 2.40, Node.js >= 24.
- [ ] Empty state root:
      `export EASY_HOST_HOME="$HOME/easy-host-v1-gate"`
      (absent or empty before the first `add`).

Record this block verbatim in the evidence:

```bash
uname -a
node -v
git --version
podman --version
podman info --format '{{.Host.Security.Rootless}}'
loginctl show-user "$USER" -p Linger
export EASY_HOST_HOME="$HOME/easy-host-v1-gate"
ls -la "$EASY_HOST_HOME" 2>/dev/null || echo "state root absent (empty)"
```

If lingering is off: `sudo loginctl enable-linger "$USER"`.


- [ ] `easy-host doctor` reports no `fail` rows. Record every `warn` row.
- [ ] Record the exact commit SHA, `easy-host version`, and the `doctor` output.

The first `add` downloads pinned Railpack and pulls BuildKit, so allow network
access and record the download time separately from the build time.

## 2. Create a two-version test repository

Use the supported Express fixture, served over `file://` so `update` can pull
new commits.

```bash
cp -r /opt/easy-host-gate/fixtures/express-api /tmp/demo-app
cd /tmp/demo-app
git init -b main
git add . && git commit -m "v1: working"
git init --bare /srv/git/demo.git
git remote add origin /srv/git/demo.git
git push -u origin main
```

Expected health response from the fixture:
`{"status":"ok","service":"express-api"}`.

Prepare these three commits up front so each scenario is a single push:

| Commit | Content | Used by |
|---|---|---|
| v1 | fixture as shipped | add, rollback target |
| v2 | change the JSON `service` string (e.g. `express-api-v2`) | successful update, rollback source |
| broken | `throw new Error("gate: broken release")` before `listen` | failed update |

## 3. Scenarios

For every scenario record: the exact commands, the observed output, the exit
code (`echo $?`), and the wall-clock time (`time <command>`).

### Scenario 1 — Add one supported repo and reach it from the LAN

```bash
time easy-host add file:///srv/git/demo.git --name demo --port 8080 --yes
echo "exit=$?"

# from the SECOND machine:
curl -fsS http://<host-lan-ip>:8080/
```

- [ ] Add exits 0 and the app is reachable at `http://<host>:8080` from the
      other machine (not just `localhost`).
- [ ] `easy-host list --json` and `easy-host status demo --json` are captured.

### Scenario 2 — Reboot brings the app back with no manual command

```bash
sudo reboot
```

After the host returns, from the second machine:

```bash
curl -fsS http://<host-lan-ip>:8080/    # no easy-host command beforehand
```

- [ ] The app serves again with `--restart=always` + lingering, and no
      `easy-host` command was run after the reboot.
- [ ] This is a **real reboot**, not `podman restart`. Record boot → serving
      wall-clock time.
- [ ] Capture `podman ps` and `systemctl --user status` evidence afterwards.

### Scenario 3 — Broken commit + `update` keeps the previous version serving

Push the `broken` commit to `main`, then:

```bash
time easy-host update demo
echo "exit=$?"
curl -fsS http://<host-lan-ip>:8080/
```

- [ ] `update` exits non-zero: health failure = 4, build failure = 3. Record
      which class occurred and the exact error text.
- [ ] The old version still serves afterwards (assert the old JSON marker).
- [ ] Capture `easy-host status demo --json` showing the failed update.

### Scenario 4 — `rollback` restores the previous image

Before this scenario there must be a **successful** v2 update so two images
exist. Sequence: push v2 → `easy-host update demo` (expect 0), then push
`broken` → `easy-host update demo` (expect failure), then roll back.

```bash
easy-host status demo --json               # record current/previous image IDs
time easy-host rollback demo
echo "exit=$?"
curl -fsS http://<host-lan-ip>:8080/       # expect the v1 marker

time easy-host rollback demo                # second rollback returns to v2
curl -fsS http://<host-lan-ip>:8080/       # expect the v2 marker
```

- [ ] First rollback serves the previous image; the second returns to the newer
      image.
- [ ] No build occurs (rollback is a health-gated image swap, seconds not
      minutes). Image IDs swap in the status JSON.
- [ ] Note: rollback with a single recorded image exits 5. That case is proven
      by `tests/integration/rollback.test.ts`, not by this gate.

### Scenario 5 — Remove deletes the app and images, keeps the volume

```bash
# re-add with a declared volume
easy-host add file:///srv/git/demo.git --name demo --port 8080 \
  --volume demo-data:/data --yes

podman exec easy-host-demo sh -c 'echo gate > /data/proof.txt'

time easy-host remove demo --force
echo "exit=$?"

podman ps -a --filter label=io.easy-host.app=demo
podman images --filter label=io.easy-host.app=demo
ls -la "$EASY_HOST_HOME/apps"
podman volume ls --filter label=io.easy-host.app=demo
podman run --rm -v easy-host-demo-demo-data:/data:ro alpine cat /data/proof.txt
```

- [ ] Container, workspace, images, and app directory are gone.
- [ ] Volume `easy-host-demo-demo-data` and its data **remain** and are
      reported by `remove`.
- [ ] Re-add the app, then `easy-host remove demo --volumes --force`; the volume
      is gone.
- [ ] A foreign volume matching the name pattern (e.g.
      `podman volume create easy-host-demo-foreign`) is reported, not deleted.
- [ ] Non-TTY removal without `--yes`/`--force` deletes nothing (exit 1).

Useful evidence helpers throughout:

```bash
easy-host list --json
easy-host status demo --json
podman ps -a --filter label=io.easy-host.app=demo
podman images --filter label=io.easy-host.app=demo --format '{{.ID}} {{.Tag}} {{.CreatedAt}}'
podman volume ls --filter label=io.easy-host.app=demo
```

## 7. What invalidates the approval

- Editing the evidence file after `approve-task` (the stored SHA no longer
  matches).
- Editing `docs/EXECUTION-MANIFEST.json` or any referenced document
  (`docs/features/06-rollback-and-remove.md`, `docs/PRD.md`) after approval —
  the digest covers the task plus its resolved references. Approve after any
  manifest recompile.
- Hand-writing or hand-editing `docs/reviews/v1-success-scenarios.json`; let the
  CLI generate it.
- Approving with a failed or unobserved scenario.

If the engine reports a dirty working tree on resume with concurrency > 1, the
blocker is uncommitted work outside `docs/`; engine state under `docs/` is
tolerated. Commit or stash the real work, or run with `--concurrency 1`.
